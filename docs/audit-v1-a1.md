# Audit V1 A1

The Control DB migration adds an event ledger and one chain state row. A1 does not
instrument business endpoints or expose an HTTP read API. The runtime module only
appends events and verifies the chain internally; it has no event update or delete
operation. Events use a closed action/object/result/reason contract. The writer
derives an account actor from a verified account session, or uses a restricted
preauthentication or CLI system context. It never accepts an actor ID from HTTP
input. UTC time and event ID are generated by the server.

**Failure contract:** `CRITICAL` throws `LehrfahrerAuditWriteFailure`; a future
caller must put the security mutation and append in one transaction and abort the
mutation if append fails. `OPERATIONAL` also throws a distinguishable failure;
the future caller must explicitly handle and surface it rather than silently
discarding it. A1 does not attach either mode to an existing action.

**Integrity:** Each event hashes the previous hash and canonical fixed fields.
The sequence and head hash are updated in the same transaction. Internal
verification detects accidental changes and unsophisticated tampering. A database
administrator with write access can rewrite both the ledger and its chain state;
strong independent proof will require a separately protected external anchor.

**DB privileges:** The deployment currently uses one Control DB credential for
both runtime and migrations. A1 logically separates the append-only module from
schema migration, but cannot enforce database-level append-only privileges with
that credential. Introducing a dedicated restricted runtime credential requires
a later hosting and migration change. The ledger is outside the webroot.

**Retention proposal:** 12 months. A1 performs no deletion or rotation. The
final retention policy and any deletion mechanism require a separate decision.
Tenant `audit.read` and platform `platform.audit.read` grant no A1 audit access;
tenant-scoped and redacted platform read APIs remain separate later phases.
